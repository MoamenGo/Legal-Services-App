> Instructions for any AI coding agent working in this repository.

## 1. Project context

- **Client:** A law firm in Riyadh, Saudi Arabia, with an existing, live website.
- **Goal:** Modernize the site to match the firm's professional identity, improve UX, and **increase qualified leads**, especially from **Google Ads** traffic.
- **Primary language:** Arabic (RTL). Secondary: English (LTR).
- **Primary audience:** Mobile visitors arriving from Google Ads and organic search looking for legal consultation.
- **Primary conversions (in priority order):**
  1. Consultation request form submitted
  2. Click-to-call
  3. WhatsApp click
  4. Consultation booked (if booking is enabled)
- **Guiding principle:** Reuse the existing site where possible. Do **not** rebuild everything unless the audit (Phase 1) justifies it and the human approves.
- **Confidentiality:** All client data, lead data, and firm information are confidential. Never send real data to third-party services that are not listed in this file.

| Testing | Vitest (unit + API via `app.request`), Playwright (E2E) |
| Lint/format | ESLint + Prettier |
| Errors/monitoring | Sentry |
| CI/CD | GitHub Actions + Wrangler |

## 4. Data models

Stored as D1 tables via Drizzle (`apps/web/src/server/db/schema.ts`). Nested objects (`source`, `{ar,en}` fields, `notes`) are JSON text columns; `ObjectId` references are text ids (UUID v7). Arrays that need querying get their own table.

Implement exactly these (add fields only with a note in `/docs/decisions`):

```ts
User        { name, email (unique), passwordHash, role: 'admin'|'lawyer'|'intake', active, lastLoginAt, createdAt }
Service     { slug (unique), title:{ar,en}, summary:{ar,en}, body:{ar,en}, faqs:[{q:{ar,en}, a:{ar,en}}],
              seo:{title:{ar,en}, description:{ar,en}, ogImage}, order, published, updatedAt }
LandingPage { slug (unique), serviceRef, headline:{ar,en}, subheadline:{ar,en},
              sections:[{type, data}], formVariant, abVariant, adGroupTags:[string], published }
Lead        { name, phone (E.164, +966...), email?, caseType, message, preferredContact: 'call'|'whatsapp'|'email',
              language: 'ar'|'en',
              source:{ utm_source, utm_medium, utm_campaign, utm_term, utm_content,
                       gclid, gbraid, wbraid, landingPage, referrer, device },
              status: 'new'|'contacted'|'qualified'|'consultation_booked'|'retained'|'lost'|'spam',
              assignedTo?: ObjectId<User>, notes:[{by, text, at}], value?,
              consent:{ privacyAcceptedAt, marketing: boolean },
              conversionsUploaded:[{ action, at, ok, error? }], createdAt, updatedAt }
Booking     { leadRef, lawyerRef, slotStart, slotEnd, mode: 'office'|'phone'|'video', status }
Article     { slug, title:{ar,en}, body:{ar,en}, authorRef, tags, seo, published, publishedAt }
Media       { key, url, alt:{ar,en}, mime, size, uploadedBy }
AuditLog    { userRef, action, entity, entityId, diff, ip, at }
Setting     { key (unique), value }   // phone, whatsapp number, office hours, GTM ID, addresses
```

Indexes required: `Lead.createdAt`, `Lead.status`, `Lead.source.utm_campaign`, `Lead.phone`, all `slug` fields (unique).

## 5. API contract

Base path `/api`. JSON only. Errors use the shape `{ error: { code, message, details? } }`.

```
POST   /auth/login | /auth/refresh | /auth/logout
GET    /services                     GET /services/:slug
GET    /landing-pages/:slug
GET    /articles                     GET /articles/:slug
POST   /leads                        (public: captcha + honeypot + rate limit 5/min/IP)
POST   /bookings                     GET /bookings/availability
GET    /settings/public

# admin (JWT + RBAC)
GET    /admin/leads?status=&from=&to=&campaign=&q=&page=
GET    /admin/leads/:id   PATCH /admin/leads/:id   GET /admin/leads/export.csv
CRUD   /admin/services | /admin/landing-pages | /admin/articles | /admin/media | /admin/users | /admin/settings
GET    /admin/reports/funnel?from=&to=&groupBy=campaign|term|landingPage
POST   /webhooks/revalidate          (shared secret; triggers Next.js ISR)
GET    /health
```

RBAC:
- `admin`: everything.
- `lawyer`: read/update leads assigned to them; read content.
- `intake`: read/update all leads; no user or settings management.

Every admin read of a lead and every write must create an `AuditLog` entry.

## 6. Lead pipeline (must behave exactly like this)

1. Client submits the form. Hidden fields carry UTM params, `gclid`/`gbraid`/`wbraid`, landing page, referrer, and device.
2. API validates with zod, checks captcha + honeypot, normalizes the phone to E.164, and saves the Lead with `status: 'new'`.
3. API responds within 500 ms. Everything else is sent to Cloudflare Queues:
   - Notify the intake team (email + WhatsApp/SMS) with lead summary and admin link. **No** full message body in SMS.
   - Send an auto-reply to the client in their language.
   - Send a GA4 Measurement Protocol `generate_lead` event (server-side backup).
4. Client is redirected to `/[locale]/thank-you`, which pushes `generate_lead` to `dataLayer`.
5. When an admin changes the status to `qualified` or `retained` and `gclid` exists, queue an **offline conversion upload** to the Google Ads API and record the result in `conversionsUploaded`.
6. Failed jobs retry with exponential backoff (5 attempts) and then alert via Sentry.

## 7. Frontend requirements

### Pages
- Home, About, Team/Lawyers, Services index, Service detail (one per practice area), Articles, Article detail, Contact, Privacy Policy, Terms, Thank-you, 404.
- **Landing pages `/[locale]/lp/[slug]`:**
  - No main navigation. Logo only, not linked away.
  - Headline that mirrors the ad keyword (`headline` field).
  - Short form **above the fold on mobile** (name, phone, case type, optional message).
  - Sticky mobile bottom bar: Call | WhatsApp | Request consultation.
  - Trust block: license/registration info, years of experience, number of cases/clients (only real numbers provided by the client), lawyer photos.
  - How it works (3 steps), FAQ, final CTA.
  - Must render fully without JavaScript (SSG).

### UX rules
- Mobile first. Design at 360px width first, then scale up.
- Tap targets ≥ 44px. Font size ≥ 16px in inputs (prevents iOS zoom).
- Phone field: Saudi format hint (`05XXXXXXXX`), accept with or without +966.
- Inline validation messages in the active language.
- Never invent testimonials, statistics, awards, or lawyer credentials. Use clearly marked placeholders (`[CLIENT TO PROVIDE]`) and list them in `/docs/content-needed.md`.
- Comply with Saudi Bar regulations on lawyer advertising. Avoid guarantees of outcomes ("we guarantee you will win" is forbidden).

### RTL / i18n
- `<html lang="ar" dir="rtl">` for Arabic, `lang="en" dir="ltr"` for English.
- Use logical CSS properties only. Never `ml-`/`mr-`/`left`/`right` for layout.
- Mirror directional icons (arrows) in RTL.
- All user-facing strings live in `messages/ar.json` and `messages/en.json`. No hardcoded text in components.
- Arabic font self-hosted via `next/font` (e.g. IBM Plex Sans Arabic), `display: swap`.

### Performance budgets (enforced in CI via Lighthouse CI)
- Mobile Lighthouse Performance ≥ 90, Accessibility ≥ 95, SEO ≥ 95, Best Practices ≥ 95.
- LCP < 2.5 s, CLS < 0.1, INP < 200 ms.
- First-load JS for landing pages < 120 KB gzipped.
- Images via `next/image` (AVIF/WebP), explicit sizes, hero image `priority`.
- Third-party scripts only through GTM, loaded `afterInteractive`. Maps and videos load lazily on interaction.

### SEO
- Unique `title` and `description` per page and locale; canonical URLs; `hreflang` alternates.
- JSON-LD: `LegalService` (site-wide), `Attorney` (team pages), `FAQPage` (service/LP FAQs), `BreadcrumbList`, `Article`.
- `sitemap.xml` and `robots.txt` generated. Landing pages are `noindex` (paid traffic only) unless told otherwise.
- **301 redirects** from every old URL to its new equivalent (`/docs/redirect-map.csv` is the source of truth).

## 8. Tracking & analytics

- Load **only** Google Tag Manager directly. GA4 and Google Ads tags are configured inside GTM.
- **Consent Mode v2:** default all storage to `denied` and update on user consent via the cookie banner. Banner is bilingual and aligned with Saudi PDPL.
- `lib/tracking/attribution.ts`: on first landing, read UTM and click IDs from the URL and persist them in a first-party cookie (90 days, first-touch + last-touch). Inject them into every lead form.
- `dataLayer` events (exact names):
  - `generate_lead` `{ lead_id, case_type, form_location, language }`
  - `click_to_call` `{ location }`
  - `whatsapp_click` `{ location }`
  - `form_start` `{ form_location }`
  - `booking_complete` `{ booking_id }`
- Enhanced Conversions: push SHA-256-hashed normalized email/phone to `dataLayer` on the thank-you page only, and only when consent allows.
- Document every tag, trigger, and variable in `/docs/tracking-plan.md`. The agent prepares the GTM container JSON in `/docs/gtm-container.json`; the human imports it.

## 9. Security & privacy (non-negotiable)

- Security headers on every response (`apps/web/src/lib/security-headers.ts` via `next.config`; `helmet` does not apply to Workers): a strict CSP (allow GTM/GA/Ads domains explicitly), HSTS, `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`.
- CORS: allow only the configured web origins.
- Rate limiting on all public endpoints; stricter on `/auth/*` and `/leads`.
- Captcha: Cloudflare Turnstile (preferred) or reCAPTCHA v3, verified server-side.
- Sanitize all rich text (DOMPurify on render, server-side sanitization on save).
- Never log full lead PII. Mask phone/email in logs (`+9665****123`).
- Secrets come only from environment variables, validated at boot in `config/env.ts`. Never commit `.env` files. Maintain `.env.example`.
- Lead data retention: a scheduled job archives leads older than `LEAD_RETENTION_MONTHS` (default 24) and anonymizes PII.
- Privacy policy page must describe what data is collected, why, retention, and how to request deletion (PDPL).
- Admin accounts: optional TOTP 2FA, account lockout after 5 failed logins (15 min).
- File uploads: images/PDF only, max 5 MB, MIME sniffing, stored with random keys.

## 10. Coding conventions

- TypeScript strict; no `any` (use `unknown` + narrowing). No `// @ts-ignore` without an explanation comment.
- Naming: `camelCase` variables/functions, `PascalCase` components/types/models, `kebab-case` file names (React components may use `PascalCase.tsx`).
- Async/await only; no unhandled promises. Hono's `onError` returns the shared error shape.
- Use the shared `logger` (pino), never `console.log` in committed code.
- Components: server components by default; add `"use client"` only when interactivity is required.
- Keep functions small and focused; match the existing style of the file you are editing.
- Comments explain **why**, not what.
- Commit messages: Conventional Commits (`feat(leads): ...`, `fix(web): ...`, `chore: ...`).
- Branches: `feat/<short-name>`, `fix/<short-name>`. Never commit directly to `main`.

## 11. Testing requirements

- **API:** Every module has Vitest tests through `app.request()` for success, validation failure, auth failure, and RBAC denial, with D1 and Queue bindings mocked (or Miniflare/local D1).
- **Shared schemas:** Vitest unit tests including Arabic input, Saudi phone formats, and malicious input.
- **E2E (Playwright), required flows:**
  1. Landing page → fill form → thank-you page → `generate_lead` present in `dataLayer` with UTM/gclid captured.
  2. Click-to-call and WhatsApp buttons fire their events.
  3. Arabic RTL layout renders correctly at 360px, 768px, 1280px (screenshot comparison).
  4. Admin login → view lead → change status to `qualified` → offline conversion job enqueued.
  5. Consent banner: tags blocked before consent, allowed after.
- Coverage target: ≥ 80% for `apps/web/src/server/api/modules`.
- A task is not done until `pnpm lint && pnpm typecheck && pnpm test` pass.

## 14. Hard rules for the agent (never break these)

1. **Never** deploy to production, change DNS, or modify the live site, live Google Ads, live GA4, or live GTM. Prepare changes; the human applies them.
2. **Never** use real client or lead data in development, tests, seeds, or prompts. Use fake data (Arabic + English).
3. **Never** commit secrets, API keys, `.env` files, or credentials.
4. **Never** fabricate content: testimonials, case results, statistics, lawyer bios, license numbers, awards. Use `[CLIENT TO PROVIDE]` placeholders.
5. **Never** add a dependency without stating why in the PR/summary. Prefer well-maintained packages; no abandoned libraries.
6. **Never** replace the stack choices in section 2 without written approval.
7. **Never** delete existing pages/URLs without a redirect entry.
8. **Never** disable tests, lint rules, or type checks to make a build pass.
9. When requirements are ambiguous, or a decision affects cost, legal compliance, or scope, **stop and ask** with 2–3 options and a recommendation.
10. Record significant technical decisions as short ADRs in `/docs/decisions/NNNN-title.md`.
